How much of the Moho file format do we actually know?

Measured, not estimated: every JSON key in the sample corpus, checked against every key the four scripts in this repository name — then checked again against Moho 14.4 itself.

The reading side is far more complete than the editing side needs it to be, and the container is already solved. A load → modify → save round-trip renders pixel-identically in Moho today. What is missing is not format knowledge but a writable document layer: the model below Layer throws away the raw dict, and nothing maintains the ~14 classes of positional index that hold a mesh together.

The percentage, with three honest denominators

A single number would be dishonest — it depends entirely on what you count. Here are all three, and which one matters for your plan.

Way of countingResultWhat it actually tells you
By distinct key name 156 / 536  29% Keys whose meaning is modelled by something that renders them. The strictest reading, and the one that best predicts "would an edit to this field do what I expect?"
By key occurrence 22.8M / 29.4M  78% Weighted by how often each key appears. Flattering but real: the format is overwhelmingly geometry and animation channels, and those are near-completely covered.
By structural description 523 / 536  98% Keys the repo's own JSON Schema declares (type, shape, enum) even where nothing consumes them. This is the number that matters for validating an edited file.
Never named anywhere 204 / 536  38% Provably untouched by all four scripts. But 45 of them are editor view-state (DocState_*) and 18 are opaque script blobs — irrelevant to rendering, and safe to carry through untouched.

Two independent counts landed on the same figure — a corpus census run here (156/536) and a separate pass over the exporters (155/536) — so the 29% is stable, not an artifact of one grep.

Already proven: a script can edit a Moho file

This was the one thing worth testing rather than reasoning about, so it was run against Moho 14.4 headless — twice, independently, on two different documents.

Experiment. Take a real project, produce two derivatives with nothing but the Python standard library, then have Moho itself render all three and compare pixels.

d = json.load(open("TransformBoneTool.animeproj"))
json.dump(d, open("base.animeproj", "w"))                    # re-dump, no edit

d2 = json.load(open("TransformBoneTool.animeproj"))
bone["anim_angle"]["val"] = [v + 0.6 for v in ...]           # rotate bone B1 by +0.6 rad
json.dump(d2, open("mod.animeproj", "w"))

Moho -r {orig,base,mod} -f PNG -start 12 -end 12

Reading. Moho's loader accepts a plain json.dump with no special handling — no byte-level fidelity required, no whitespace ceremony, no checksum. The edit landed exactly where intended. Moho's own manual (Appendix F) documents this workflow and ships sample Python for it, so this is a supported path, not a hack.

Two caveats found while proving it. First, byte-identical output is not reproducible with any stdlib json.dumps preset — Moho writes indent=2 in v1045 and fully minified JSON in v1038, and float formatting differs either way. That costs diff-friendliness, not correctness. Second, and this one is a real bug: constructing a Document mutates the raw dict — _resolve_patch_layers overwrites every PatchLayer's own parent_bone, flexi_bone_subset and origin with its target's. Since a patch's own transform is its clip region, loading a document with patches and re-saving it would corrupt it. Eight patch layers exist in the corpus.

The knowledge assets, ranked by what they settle

Worth knowing what already exists before commissioning any new investigation — three of these are outside authorities, not this repo's own guesses.

pkg_moho.lua_pkg
Moho's own scripting header, inside the app. Declares the C++ struct members in the order the JSON writes them. 43 classes, 396 data members, 128 enum constants in 22 families. M_Bone alone has 64.
Highest authority, cheapest to consult. Read before inferring any field.
schema/*.schema.json
A draft-2020-12 JSON Schema of the whole format — 6 files, 63 $defs, 471 declared keys. Covers 523 of the 536 corpus keys; the 13 misses are all rare (skia_scaling, three psd_*, one document's masking_points).
The validation gate an editor needs. Corpus-derived, so it describes what these 46 files contain — not Moho's whole output space.
Moho CLI twin renders
Render the same document twice with one field flipped; the difference is that field's effect, with every unrelated modelling error cancelled out. This settled fixed_angle, mask_expansion, stroke exposure, the bone spring and both masking enums.
The method that resolves anything still open. ~2s per frame.
docs/moho14 · Appendix F
Moho's own file-format appendix. Confirms .moho is a plain ZIP holding Project.mohoproj + preview.jpg, that unknown keys are silently ignored by older versions, and that additive writes are safe.
But it states outright that layer properties are "too many to name" — there is no official complete field reference. Anywhere.
The two writers
svg2moho.py and lottie2moho.py already emit valid documents at exact real-file field counts for mesh, points, curves, shapes and styles. 465 converted Lottie files load in Moho 14.4; a 166-layer SVG converts and renders.
Carries the hardest-won knowledge: the loader's validity rules, with exact error strings.
mohoscripts/ · 197 Lua scripts
Third-party scripts calling Moho's real API — a second opinion on behaviour. Corroborated asymmetric bone scale, flip propagation, the control-bone model, and supplied the cycle formula.
Evidence only. One carries an arithmetic slip; another is right only at default camera zoom.

What the writers already learned the hard way

These are the rules that make Moho reject a file, each recorded with the exact error it produces. They are worth more than any field list, because they are invisible until you hit them:

  • Omitting document-scaffold keys (onions_*, metadata, documentviewstate) → "Unable to load document (corrupt)", error 108 — even though this repo's own reader loads such a file happily.
  • A bare scalar where a channel belongs → "Type mismatch: got OBJECT expected DOUBLE". Point positions, widths, smoothness, all colours must be full {type,ref,mute,when,val,interp} objects.
  • noise_grain / pixelation are integer 0, not false — JSON false gives error 108.
  • mesh.anim_shape_order is a plain bool; the channel form fails.
  • global_render_style_* must be 0 or every gradient renders flat.

The real obstacle is not knowledge — it is index integrity

Value-level edits are available today. Structural edits — adding or deleting a point, curve, shape, bone or layer — need machinery that does not exist yet, because the mesh interior is held together almost entirely by positional indices with no allocator and no generation counter.

ReferencePoints atKindWhat breaks it
shape.edges.curve[i]mesh.curves index Deleting one curve invalidates every reference above it.
curve.points[i].pointmesh.points index Curves store no coordinates — position is shared through this index.
mesh.points[i].curves[]curve + point indices index The reverse map. This repo rebuilds it and ignores the stored one; Moho does not — an editor must maintain it.
mesh.points[i].parentancestor skeleton's bones index Per-point bone binding. Real on ~4,000 points across 119 meshes.
layer.parent_bone, bone.parent, bone.target_bone, the three *_control_parentsame skeleton's bones index Reordering or deleting a bone silently repoints all of them. target_bone hides its index inside an animated channel.
layer.flexi_bone_subsetbones index Bone indices as a pipe-joined string ("30|31|32") — not names.
position in mesh.shapes— order List position is the z-order, and combo_mode boolean groups are built from adjacency in it. Reordering changes both stacking and boolean combination.
shape.edges.flag— trap Looks like a direction bit; measurably is not. Loops are re-traced as an undirected graph keyed on rounded coordinates — so moving a point can change the traced topology.
layer.uuid → target_layer_uuid, follow_layer_uuid, distortion_layer_uuid, layer_ref_uuidlayers uuid The one genuinely robust reference class. Survives reordering.
inherited_style_uuid / _namedoc.styles name or uuid Either key works, and it may sit on the shape or inside the shape's own style — both occur in real files. Deleting a style silently reverts shapes to inline defaults, with no error.
switch_keys valueschild layer names name Renaming a switch child silently breaks the animation; the fallback is child 0.
Smart Bone dialbone.name = registered action name name, 3-way The most dangerous rename in the format. The name registry is replicated on nearly every layer (19,921 entries), the pose bodies live inside per-channel actions[] (11,816 of them), and Moho stores two actions per dial with the second suffixed " 2". Renaming a bone silently de-activates its Smart Bone.

Compounding this: the document model is only writable down to Layer. Mesh, Shape, Curve, CurvePoint, MeshPoint and Bone are lossy extractions that discard their source dict — Shape keeps 9 of 17 keys, MeshPoint 3 of 11, Bone ~35 of 61 — and Document retains no root dict at all. The workable pattern today is to keep the raw dict alongside the Document and edit the raw dict. There is also no round-trip test anywhere in the repo; the one specified in the Lottie plan is format-crossing and still open.

What I need to go further

Ordered by how much each unlocks. The first three are things only you can supply; the rest is work this repo can do on its own once scoped.

  1. Sample documents for the areas with no data

    Several features cannot be decoded because the corpus has no evidence of them — not because they are hard. Nothing can be measured from zero instances:

    • Zero samples: AudioLayer (Moho declares the class; the corpus has none), Mesh3DLayer, a non-empty layercomps, a non-empty action_refs, any document with 3d_mode != 0.
    • One or two samples — not enough: ParticleLayer (2), NoteLayer (1), Vitruvian bones_groups (1), mesh.groups point groups (1), masking_points (1), Smart Warp / squashable_deformer (10, none with a reference render).
    • Present everywhere, never exercised: IK and bone constraints sit in 43 of 46 documents but appear to be at defaults throughout. A rig that actually uses IK locks, angle constraints and ignored_by_ik would unlock the largest single 0% area.

    Only you can supply this. Rigs you save from Moho yourself are ideal — a deliberately built one beats a found one, because you know what you turned on.

  2. Which container do your users actually hand you?

    .moho is a ZIP holding Project.mohoproj — and none of the four scripts read it. They all take bare .mohoproj/.animeproj. If real input is .moho, that is a small, mandatory piece of plumbing on both the read and write side, including regenerating or preserving preview.jpg.

    One answer from you, then roughly an hour of work.

  3. Which editing operations matter first

    The gap between "value edits" and "structural edits" is the difference between days and weeks. Value edits — move points, recolour, retime channels, toggle visibility, rewrite bone angles, swap image paths, rename layers — work today with the raw dict. Structural edits need the index-renumbering layer described above.

    If you can name the ten operations a user would most want to script, that ordering determines whether the untouched 38% matters at all. Most of it — DocState_*, g_* flags, editor state — an editor should preserve untouched rather than understand.

    A decision from you. This is scoping, not research.

  4. Let me build the missing foundation

    Three concrete pieces, in dependency order, none of which needs new format knowledge:

    • A writable document layer — keep _raw on Mesh, Shape, Curve, MeshPoint, Bone, and give Document its root dict back. Fix the PatchLayer load-time mutation first; it is a live corruption bug.
    • A round-trip test in tools/: load → dump → compare, over all 46 documents, plus a Moho-render diff on a few. Both halves are proven to pass right now, which makes this the cheapest regression net available.
    • An integrity checker that validates the index graph and the three name-based couplings after any edit, wired to schema/ for structure. This is what turns "the file loads" into "the file is correct".

    Just say go. No new evidence required.

  5. Then close the measurable unknowns by twin render

    Everything still open in the 0% areas is decodable by the same method that decoded the rest: write a synthetic document with one field set, render it twice with Moho, diff. In rough value order — binding_mode and scaling_mode (43 docs, and scaling_mode is the likely cause of a preserved asymmetric-scale oddity), the b[] Bezier easing handles (the data is sitting in the file, only ao is read), layer_ordering / animated_layer_order, SS_Halo (198 shapes — the single biggest appearance gap), blend_mode 4–13, target_layer_id, switch_interpolation.

    This repo can do it unattended — but note that reference SVGs cannot validate the blurred/composited effects. Moho's own SVG export drops them; those need PNG renders.

How these numbers were produced

Every .mohoproj/.animeproj under moho/ was parsed — 46 files, 0 parse failures, format versions 1021 / 1038 / 1039 / 1045 — and every key recorded with its occurrence count, document count, contextual paths, value types and examples (536 distinct keys, 29,380,843 occurrences). Each key was then searched as a quoted string literal across moho2svg.py, moho2lottie.py, svg2moho.py and lottie2moho.py. A key found in no source file is provably unread; the converse is a slight over-count, since a matching literal is not proof the value is used semantically. Channel keys (when/val/interp/actions) are consumed generically, which pushes the true figure marginally the other way. The two errors are small and opposing.

Scripts: tmp/key_inventory.py, tmp/key_context.py, tmp/coverage_by_area.py — all re-runnable. Round-trip renders were produced with Moho -r … -f PNG and compared per-pixel; the feature-area grouping is a hand-authored classifier in coverage_by_area.py, which attributes 372 of the 536 keys and leaves 164 shared names unattributed. Class, member and enum counts come from pkg_moho.lua_pkg by grep, not estimate.
